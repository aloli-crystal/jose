== v0.2.0 — 2026-09-19

=== Added

* **RSA support.** `Jose::JWK::RSAKey` and the `RS256`, `RS384` and `RS512`
  signature algorithms. The driver is OpenID Connect and WebAuthn: both sign
  with RS256 by default, so an EC-only library cannot verify a token from a
  typical identity provider nor an assertion from a Windows Hello
  authenticator.
* `RSAKey`: key generation, JWK parsing and serialization, RFC 7638
  thumbprints, `modulus_bits`, and DER output as PKCS#1, PKCS#8 and
  SubjectPublicKeyInfo.
* `Jose::JWS::Family` and `Algorithm#family`, so an algorithm and a key type
  can be checked against each other. Signing with `RS256` and an `ECKey`, or
  `ES256` and an `RSAKey`, now raises instead of failing obscurely.
* `JWS.sign_data` and `JWS.verify_signature`, to produce and check a bare signature over arbitrary data
  outside any JWS envelope — what WebAuthn needs, where an authenticator
  signs its authenticator data concatenated with a client-data hash. ECDSA
  signatures are taken in ASN.1 DER, OpenSSL's native form, which is also
  what authenticators emit.
* `Jose::DER`, a small shared DER encoder/decoder. `JWS` used to carry its own
  private copy for ECDSA signature reshaping; both it and `RSAKey` now use
  this one.
* Interop specs against the `openssl` binary. RSASSA-PKCS1-v1_5 is
  deterministic, so our signatures are compared **byte for byte** with
  OpenSSL's own — a complete check of padding, digest and key handling, not
  merely a round-trip against ourselves. Skipped when `openssl` is absent.

=== Fixed

* README usage examples still referred to `CrystalJose::*`, renamed to
  `Jose::*` back in v0.1.2.

=== Notes

* RSA keys are built through the EVP-level `d2i_PUBKEY` and
  `d2i_AutoPrivateKey` entry points rather than the low-level `RSA_new` /
  `RSA_set0_key` family, which OpenSSL 3 deprecated.
* A private `RSAKey` needs its CRT members (`p`, `q`, `dp`, `dq`, `qi`) in
  order to sign. RFC 7518 makes them optional in a JWK, but OpenSSL cannot
  build a key from `n`, `e` and `d` alone; `#crt_complete?` reports whether
  they are present. Verification with a public key is unaffected.
* Key generation refuses anything below 2048 bits.
* RSA-OAEP, RSA-PSS (`PS256`, …) and EdDSA remain out of scope.

== v0.1.2 — 2026-04-29

=== Changed

* **Internal module renamed** `CrystalJose` → `Jose` (Aloli convention:
  drop the `Crystal` prefix and use strict CamelCase — no acronym
  preservation, even for protocol families like JOSE).
* Source folder `src/crystal_jose/` → `src/jose/`. Entry-point
  consolidated into `src/jose.cr`. Internal `require` paths updated.
* Behaviour and public API unchanged.

=== Note for consumers

External code that referenced `CrystalJose::*` (`clevis-geli`,
`clevis-zfs`) needs to be updated to `Jose::*` and re-pinned to
`~> 0.1.2`.

== v0.1.0 — 2026-04-27

Initial release. Scope intentionally limited to what
`crystal-clevis-geli` (Tang client) needs.

* **JWK** (RFC 7517, RFC 7518 §6.2, RFC 7638): EC keys on
  curves P-256, P-384, P-521. JSON parsing and serialization,
  public-key extraction, thumbprints validated against
  https://github.com/latchset/jose[latchset/jose].
* **JWS** (RFC 7515): Compact Serialization. Algorithms
  ES256, ES384, ES512 (sign and verify). Correct DER ↔ R||S
  conversion (validated with 50 random round-trips per curve).
* **JWE** (RFC 7516, RFC 7518 §4.6 + §5.3): Compact
  Serialization. ECDH-ES key agreement + A256GCM content
  encryption. Concat KDF as specialized in RFC 7518 §4.6.2.
* **Interoperability** with `latchset/jose` validated end-to-end:
  thumbprints, JWS sign/verify cross, JWE encrypt/decrypt cross,
  ECDH shared-secret derivation.

Out of scope for v0.1 (and not currently planned):

* RSA-based algorithms.
* EdDSA (Ed25519).
* Full JWT validation (`exp`, `nbf`, `aud`, …).
* JWE General/Flattened serializations (only Compact is supported).
